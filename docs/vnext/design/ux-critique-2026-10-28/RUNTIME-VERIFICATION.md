# Runtime evidence, version reconciliation and open verification questions

**Source date:** 2026-10-28. **Read before declaring Hike absent or calling a visual bug fixed.** This note supplements the code audit and the earlier public-site walkthrough.

## What the live walkthrough could and could not establish

A public browser walkthrough of `https://opengravel.henning.rodeo/` attempted to find the Hike switch from the Map and Explore pages. It **did not locate the control** and did **not reach the Settings activity section** before stopping. It could inspect the existing motorcycle Map and Explore controls, but **could not open a Hike trail detail or test phone Hike layout**.

The browser's autogenerated conclusion that “Hike mode does not exist” is **not supported** by the rest of the evidence and **must not be repeated as fact**. Current main contains:

- `src/ui/planner/ActivitySwitch.tsx`: a real Ride/Hike radiogroup;
- `src/ui/nav/AppMenu.tsx`: mobile/tablet menu renders the activity switch;
- `src/ui/settings/SettingsSurface.tsx`: Settings renders the activity choice;
- `src/app/ExploreClient.tsx`: `mode === "hike"` renders `HikeExplore`;
- `src/app/HikeExplore.tsx`: trail list and trail detail pages;
- `src/ui/planner/HikeActivityControls.tsx`: map Hike controls; and
- dedicated Hike router and critical Playwright test files.

This is an **inconclusive end-to-end live accessibility/discoverability check**, not a finding of zero Hike functionality.

A second read of the public site's rendered HTML for `/settings` showed an **Activity → Planning activity** section, but did not expose the complete hydrated Ride/Hike controls in extracted text. This cannot independently confirm the control's clickable state.

## Most plausible explanations to investigate — not assertions

1. **Desktop discoverability:** the `AppMenu` is intentionally phone/tablet-only; desktop Settings is reached through the global header link. A first-time desktop hiker may not know to navigate to Settings → Activity. This is a likely **information architecture** problem, not proof the feature is absent.
2. **Deployment revision:** production might be on a different commit from current `main`. Inspect real deploy version/manifest (without secrets) rather than assuming GitHub main == live site. Do not redeploy just to make this check pass.
3. **Client hydration or feature state:** automatic extraction may miss client controls while initial SSR text still shows headings, or may stop before the right click. Inspect the browser DOM and actual visible screen rather than relying on one text transcript.
4. **Viewport differences:** mobile/tablet users may have `AppMenu` with an activity switch that desktop does not present in the same position. Verify each breakpoint separately.
5. **Browser state:** activity mode persists in localStorage, so a clean browser and existing user's browser can show different states. Explicitly test both.

## Required live verification protocol for Claude

1. Record the deployed build/commit identity when legitimately exposed by an existing status/health/version field. Don't guess version from source.
2. Run a **fresh desktop** navigation script: Map → Settings → Activity → Hike → Map → Explore hikes → real trail detail → Back → switch Ride.
3. Run a **clean iPhone-size browser**: Map → top Menu → Activity → Hike → plan/sketch → Explore hikes → detail, and compare at 320/390/440px.
4. Inspect *actual DOM and captured screenshots* after each click; reject blank/loading/incorrect screenshots, and record exact labels and URLs.
5. Test a returning visitor with `og-activity-mode=hike`, as well as a first-run `ride` preference; note nav/labels in both.
6. If Hike is unavailable, classify the reason separately: no clickable selector; app script/hydration failure; feature data empty; catalog backend unavailable; hike router unconfigured; unauthorized browser state; or deployment mismatch.
7. Do not modify live data or start real activity unless explicitly in a safe test environment. Use deterministic route fixtures and a separate live-provider smoke test.

## Product implication regardless of deployment state

Having a Hike switch in Settings/code is **not the same** as making Hike discoverable to a person who opens the Map to hike. Claude should evaluate whether an activity indicator beside search or a first-use choice would materially improve discoverability; changing the locked top-level navigation design requires deliberate owner approval rather than silently adding a fourth tab.

Do not create new stand-alone Ride and Hike apps merely to solve discovery. The recommended outcome is **one coherent Map/Explore shell with visible context and activity-aware content**.

## Screenshot evidence standard

To qualify as a confirmed visual defect, include viewport, theme, activity, app/deploy version, state, screenshot with no loading overlay, exact observed region and reproducible steps. A code comment or test `fixme` is evidence of a **documented gap**, not visual proof that a specific current live viewport still fails.

**Status to preserve in handoff:** Hiking exists in the repository; live discovery and full current production hiking flow remain **unverified** in the walkthrough. This uncertainty should be resolved before any claim that Hike is absent, shipped, accessible or fully working.
